# Практики из монолита Hexlet

Разбор `~/projects/work/hexlet` — основного приложения Hexlet: **Rails 8.1 + Inertia 3 + React 19 + Mantine 9 + Sorbet**.

Почему этот разбор важнее [разбора hexlet-college-spa](spa-practices.md): монолит — первоисточник. Практики, которые в spa выглядят «перенятыми из рельсы», перенесены именно отсюда — совпадают структура словаря (`models.attributes.base`, `helpers.actions`), скоуп флеша от контроллера, `render` по конвенции, раскладка страниц. И, в отличие от spa, монолит стоит **ровно на том стеке, куда едет hexlet-sicp** (Inertia + Mantine + TS + SSR), причём уже несколько лет.

Ссылки на файлы — относительно корня `~/projects/work/hexlet`. Читал только на чтение, ничего не менял.

Сам монолит подробно документирован изнутри: `AGENTS.md` (30 КБ, правила), `ARCHITECTURE.md` (27 КБ, границы слоёв), `CONTEXT.md` (124 КБ, доменный язык). Ниже — выжимка того, что переносимо.

## 1. Слои бэкенда и границы между ними

`ARCHITECTURE.md` фиксирует не просто список папок, а правила выбора между ними — это и есть главная ценность.

| Слой | Что там | Чего там не бывает |
|---|---|---|
| `app/models/` | поведение одной сущности, валидации, ассоциации | query-логика, оркестрация сценария |
| `app/models/concerns/` | переиспользуемые миксины | |
| `app/repositories/` | модули с query-логикой (scopes, SQL), подключаются в модель через `include` | бизнес-логика |
| `app/structs/` | типизированные DTO **входных** параметров, `<Entity><Action>Struct` | DB-aware валидации, бизнес-правила, сами сущности |
| `app/resources/` | DTO-сериализаторы **выходных** данных (Alba) | |
| `app/services/` | use case целиком, оркестрация | query-логика, технические хелперы, поведение одной сущности |
| `app/mutators/` | фабрики моделей — замена колбеков | оркестрация сценария |
| `app/handlers/` | тонкая адаптация событий → вызов сервиса своего домена | бизнес-логика |
| `app/lib/` | инфраструктура и технические утилиты | |

Правила, которые интереснее самой таблицы:

- **Сервис — не classes-as-functions.** Один сервис на *сущность*, плоское имя `<Entity>Service`, внутри несколько class-методов по сценариям (`create`, `update`, `archive`, `move_member_to_group`). Никаких `CourseUpdateService` и `Service.call(...)`. Экшен контроллера соответствует методу сервиса один-в-один.
- **Сервис возвращает `Typed::Result[Payload, Payload]`**, где `Payload` — структура, объявленная внутри самого сервиса, и содержит всё, что контроллеру нужно для редиректа или рендера. Контроллер берёт `result.payload.foo` и **не делает повторный `find`** после вызова сервиса.
- **Сервис сам находит сущность по `id`.** Модель снаружи не принимает — иначе контроллер дублирует «нашёл, передал».
- **`current_user` передаётся явным параметром**, `CurrentAttributes` в сервисах запрещены: сервис должен быть вызываем из теста, консоли и джобы, где request-контекста нет.
- **События — только между доменами.** Внутри одного use case порядок выражается прямыми вызовами в сервисе: «сервис должен читаться сверху вниз и показывать всю последовательность». Разбивать сценарий на события «чтобы красивее» запрещено — это прячет процедуру от ревью. Если издателю нужен результат подписчика — это не событие, а вызов.
- **Rake-таск — однострочный вызов метода сервиса.** Причина техническая и убедительная: Sorbet не типизирует `.rake`, а тесты его тело не покрывают — то есть `.rake` слепая зона сразу для двух проверок.

Для hexlet-sicp тут важна не буква (у нас есть `app/Services`, `app/DTO`, презентеры), а разделение **входных** и **выходных** DTO как отдельных слоёв: `structs` ≠ `resources`. У нас сейчас 9 DTO — все входные, и план миграции честно пишет, что для пропов нужны новые, выходные. Монолит подтверждает, что это не удвоение работы, а норма.

## 2. Флеш: `f(:success)` и цепочка ключей вверх по иерархии контроллеров

`app/controllers/concerns/flash_concern.rb` — это канонический вид того приёма, который в spa сделан наполовину. Контроллер пишет одно:

```ruby
f(:success)
f(:error, now: true)
```

Ключ собирается из пути контроллера, экшена и типа, а затем **хелпер идёт вверх по цепочке суперклассов**, подставляя `base` вместо экшена, и отдаёт весь список как `default` в `I18n.t`:

```
flash.web.management.blog_post_categories.create.success   ← самый конкретный
flash.web.management.application.base.success              ← родительский контроллер
…до ActionController::Base
```

То есть фоллбек не прописан руками, а получается из иерархии контроллеров: общий текст живёт на базовом контроллере, конкретный — рядом со своим экшеном, и переопределяется по мере надобности. Плюс `options[:values]` для интерполяции и цветной вывод флеша в лог для отладки.

Это ровно то, что я предлагал в [spa-practices.md §11.2](spa-practices.md), только продуманнее: **фоллбек через наследование контроллеров вместо одного захардкоженного `layout.flash.<type>`**. Брать надо этот вариант.

## 3. Списки: один проп `grid` вместо трёх

`app/controllers/application_controller.rb::grid_params` + `app/resources/grid_resource.rb`. Пагинация, сортировка и фильтры едут на фронт **одним объектом**:

```ruby
attributes :sf, :so, :page, :tr, :per, :fields   # sort field, sort order, page, total records, per page, фильтры
attribute :first { (it.page - 1) * it.per }
```

Контроллер:

```ruby
default_params = { sf: "id", so: "desc" }
query = ransack_params(default_params)
search = BlogPost::Category.with_locale.ransack(query)
pagy, categories = pagy(:offset, search.result)

render inertia: true, props: {
  categories: BlogPostCategoryResource.new(categories),
  grid: GridResource.new(grid_params(pagy, default_params)),
}
```

Три вещи стоит отметить:

- **`render inertia: true`** — имя страницы выводится по конвенции из контроллера и экшена. Это первоисточник нашего `Controller::inertia()`;
- **параметры списка короткие и единообразные** (`sf`/`so`/`fields`), а дефолты задаются в экшене и уходят на фронт вместе с данными — фронт всегда знает текущее состояние грида, не парся URL;
- **фильтрация верхнего уровня — в контроллере/репозитории, не в ресурсе.** В `ARCHITECTURE.md` отдельно описана ловушка Alba: у `has_many` с заданным `resource:` блок `do…end` **молча игнорируется**, и фильтр в нём мёртв. Фильтр передаётся вторым позиционным Proc-аргументом. У нас аналогов Alba нет, но урок общий: сериализатор — не место для фильтрации.

У hexlet-sicp план предполагает `{ items: XData[], pagination: PaginationData }` и отдельный `Filter.tsx`. Конверт `grid` — на один проп меньше и на одну согласованность больше; сортировки у нас нет вообще, так что поля `sf`/`so` можно просто не заполнять.

## 4. Формы: отдельный «crud»-ресурс на сущность

Ключевая находка. Для одной сущности живут **два** выходных DTO:

- `BlogPostCategoryResource` — для списка и показа;
- `BlogPostCategoryCrudResource` — для формы, отдаётся пропом `categoryCrud` в `new`/`edit`.

Из второго генерируется TS-тип `<Entity>Crud`, а на фронте `app/javascript/lib/crudBuilders.ts` собирает объект этого типа с дефолтами:

```ts
export function buildStackModuleCrud({ stackId, stackModule = null }): StackModuleCrud {
  return {
    id: stackModule?.id ?? null,
    name: stackModule?.name ?? null,
    stack_id: stackId,
    state: stackModule?.state ?? 'active',
  }
}
```

Один билдер обслуживает и create (сущности нет — все дефолты), и edit (сущность есть — её значения). Это то же, что `lib/forms.ts` в spa, но тип объекта **генерируется из бэкенда**, а не пишется руками, поэтому форма не может разъехаться с сериализатором.

Вход — struct с валидацией только формы данных:

```ruby
class BlogPostCategoryCreateStruct < T::Struct
  include ApplicationParamsStruct::Base
  const :name, T.nilable(String)
  const :slug, T.nilable(String)
  validates :name, presence: true
end
```

Причём `permit` выводится из набора полей автоматически — то есть strong parameters не дублируются. Невалидный struct бросает исключение, которое ловит **глобальный** `rescue_from` в `Web::ApplicationController` и делает `redirect_back_or_to(..., inertia: { errors: e.errors })`; ручного `valid?`-флоу в экшене нет.

Передача струка дальше — **только сплатом**: `Model.new(**struct.to_h, locale: System.language)`, никаких пофайловых `name: struct.name, …`.

Ошибки модели нормализует `IdBasedErrors.for(category)` — единая форма ошибок для Inertia.

## 5. Генерация Rails → TypeScript и правило про генераты

Что генерируется (`AGENTS.md`, раздел «Интеграция Rails → TypeScript»):

| Источник | Артефакт |
|---|---|
| `app/resources/**` (Alba + typelizer) | `app/javascript/types/serializers/` |
| enum-ы моделей | `app/javascript/generated/enums.ts` |
| имена моделей | `app/javascript/generated/modelNames.ts` |
| имена событий Rails Event Store | `app/javascript/generated/eventNames.ts` |
| маршруты Rails | `app/javascript/routes.js` + `routes.d.ts` |
| словари локалей | `app/javascript/types/resources.d.ts` |
| схема БД | аннотации в моделях (`annotaterb`) |

Всё это собирается одной целью:

```make
sync: sync-types sync-locales sync-fixtures sync-annotations sync-routes sync-browserlist sync-rbi lint-fix
```

И два правила вокруг генератов, которые стоят отдельного внимания:

- **«Автогенерируемые файлы никогда не правим руками — меняем источник и перезапускаем генератор.»**
- **«Вывод генератора не откатываем, независимо от объёма диффа: если сгенерилось больше, чем ты менял, значит так и надо — коммитим весь вывод как есть.»**

Второе — про дисциплину ревью: соблазн «причесать» лишние 200 строк диффа в сгенерированном файле ломает воспроизводимость. У нас в план миграции уже заложены `make generate-types` и `make types-check` (`git diff --exit-code` на генерат) — это техническая половина того же решения; вторая половина словесная и её стоит записать в `AGENTS.md`.

## 6. Переводы: типизированные ключи готовым инструментом

Здесь монолит закрывает главную рекомендацию из разбора spa — и оказывается, что свой генератор писать не надо.

`i18next.config.ts` в корне:

```ts
types: {
  input: ["app/javascript/locales/ru/*.json"],
  output: "app/javascript/types/i18next.d.ts",
  resourcesFile: "app/javascript/types/resources.d.ts",
  enableSelector: true,   // type-safe key selection
}
```

`i18next-cli` генерирует `resources.d.ts` (6013 строк) из русского словаря, а `enableSelector: true` включает селекторный API i18next, и ключи пишутся **колбеком, а не строкой**:

```ts
t(($) => $.blocks.calendar.today)
```

Опечатка и несуществующий ключ — ошибка компиляции. Строковый стиль `t("...")` в `AGENTS.md` прямо запрещён. Плюс тот же CLI умеет `extract` (вытащить использованные в коде ключи в JSON) и `sync` (выровнять локали между собой) — в монолите это `make sync-locales` вместе с `i18n-tasks normalize`.

**Структура словаря** (`app/javascript/locales/ru/translation.json`, верхний уровень):

```
layouts      строки лейаутов (header, footer, management_layout, my_layout, …)
breadcrumbs  подписи крошек
blocks       переиспользуемые блоки и модалки
enums        человекочитаемые значения enum-ов, по модели
models       names + attributes.base + attributes.<model>
common       общие строки, ошибки, ссылки
links        ссылки
pages        строки конкретных страниц, сгруппированные по разделу
helpers      action / boolean / crud / state / submit
```

Отсюда spa и взял `models.attributes.base` и `helpers.actions` — совпадение буквальное. `models.attributes.base` держит общие подписи (`created_at`, `email`, `name`, `state`, …), а `models.attributes.<model>` — специфичные; поле формы сначала ищет в своей модели, потом в `base`.

Ещё два правила: составная строка собирается через `<Trans />`, а не склейкой в TSX; словарь-источник — русский, остальные локали подтягиваются синхронизацией.

**i18n спроектирован под SSR** (`app/javascript/lib/i18n.ts`): не модуль с сайд-эффектом, а фабрики — `createServerI18n(language)` для сервера и `getClientI18n(language)` с мемоизацией для браузера, плюс `buildInitialI18nStore(language)`, отдающий только нужную локаль. Наш план миграции уже пишет «`i18n.ts` — фабрика `createI18n({lng, resources})` вместо модуля с сайд-эффектом» — то есть направление угадано, а здесь есть готовая референсная реализация, включая мемоизацию клиентского инстанса.

## 7. Правила Mantine

Короткий, но плотный раздел `AGENTS.md`:

- **используем только компоненты Mantine, без обычных React-тегов**;
- **в style props только токены (`sm`, `bold`) и никогда конкретные числа**;
- **`any` под запретом**, типы конкретные;
- **всегда учитываем SSR**;
- правишь фронтенд — `make lint-fix`.

Первые два правила в нашем плане миграции не зафиксированы, а стоят дорого: именно от них зависит, будет ли редизайн выглядеть как одна система. Третье и четвёртое у нас есть (`strict`, SSR-правило).

## 8. Правила кода и тестов, которые стоит забрать дословно

Из `AGENTS.md`. Отобрал то, что применимо к Laravel-проекту почти без перевода:

**Контроллеры и модели**

- **Нельзя создавать обычные методы (не экшены) в контроллерах.** Вспомогательный метод — признак, что логика не на своём слое.
- **`order` никогда не зашивается в scope** или в блок ассоциации: «скоуп = WHERE; сортировка — отдельное решение точки использования». Скрытый `order` ломает индексы, удивляет при eager loading и невидим в месте вызова.
- **Soft-delete — отдельное измерение от бизнес-состояния.** `state` только для `draft`/`published`, «удалено админом» — через `discarded_at`. Индексы по умолчанию через `.kept`.
- **У моделей предикаты на все поля**: `user.email?`, а не `user.email.present?`.
- **Дефолт enum-поля задаётся в модели, а не в миграции** — «бизнес-решение должно быть видно в Ruby-коде, а не спрятано в схеме базы».
- **Миграции: schema и data — разные файлы**, и миграции forward-only: накатанное не откатываем, исправляем новой миграцией вперёд.
- **Единая точка получения локали** — `System.locale` / `System.language` (`app/lib/system.rb`), а не `I18n.locale` напрямую; в маппинге, например, `kz → ru`. У нас с mcamara и локаль-префиксом это больное место ровно того же вида.

**Стиль**

- **Разделяй получение и использование:** получил — записал в переменную — дальше передаёшь переменную.
- Вложенные тернарники не используем; `unless` только с унарными операциями.
- Комментарии — только для неявного поведения.
- Развёртка «небезопасного» значения (`T.must`) — отдельным выражением в переменную, не инлайном: «инлайн теряется при чтении и плохо ловится по diff».

**Тесты**

- **На каждый экшен обязателен интеграционный тест** — безусловное правило, а не «по просьбе». Юнит-тесты — только когда просят.
- **Только позитивные сценарии**; проверяем код возврата и, если надо, данные в БД.
- **Подготовка данных только через фикстуры/фабрики**, а не изменением кода теста.
- **`reload` — всегда отдельной инструкцией**, никогда частью цепочки.
- **Внешние вызовы закрываем webmock, стабы не делаем.**
- Перед push — только тесты, один раз по готовности ветки; линт висит на pre-push хуке.

**Sentry** (у нас подключён, а правил нет)

- **Текст `capture_message` — константа без интерполяции.** Текст и есть фингерпринт: `"Tutor id: #{id} …"` заводит отдельную иссью на каждого пользователя. Переменное уходит в `set_context` (читать) и `set_tags` (фильтровать).
- **Коммит, меняющий текст сообщения, обязан это назвать** — старая иссью после правки замолкает, и следующий разбор читает тишину как фикс. В монолите на этом почти закрыли живой баг.

**Отладка**

- Маршрут проверяется без браузера и без теста: `bin/rails console -e test` → `app.get "/path"` → `app.response.status`, а подробности (SQL, рендеры) читаются в `log/test.log`, не в stdout. Прямого аналога `app.get` в Laravel нет, но принцип «сначала лог, потом вывод раннера» переносится буквально: при падении тестов причину искать в `storage/logs`, а не только в выводе PHPUnit.

## 9. Что забрать в hexlet-sicp — с поправками к разбору spa

Дельта относительно уже сделанного и уже запланированного (см. [spa-practices.md §10](spa-practices.md)).

### Поправки к вчерашним рекомендациям

1. **Типы для ключей переводов — не свой генератор, а `i18next-cli` + `enableSelector: true`.** Вчера я предлагал написать артизан-команду, генерящую `.d.ts` из `resources/lang/**`. Правильнее взять готовое: `i18next-cli` уже делает и типы, и `extract`, и синхронизацию локалей. Наша специфика в том, что источник — PHP, а CLI ждёт JSON, поэтому цепочка получается из двух шагов: артизан-команда выгружает **шипящиеся группы** (те самые 12 из ADR 0003) в JSON, `i18next-cli` генерит по ним типы. Побочная выгода — выгрузка становится тем же артефактом, который читает i18next в рантайме, то есть `TranslationBag` и типы гарантированно про одно и то же. И ключи пишутся как `t(($) => $.admin.users.title)`.
2. **Флеш по ключу — брать реализацию монолита, а не spa.** Цепочка ключей вверх по иерархии контроллеров (§2) решает проблему фоллбека лучше, чем один общий `layout.flash.<type>`, который я предлагал: общий текст живёт на базовом контроллере, конкретный переопределяется рядом со своим экшеном.
3. **Структуру словаря не изобретаем.** Целевая раскладка уже канонизирована в монолите (§6) и продублирована в spa: `layouts / breadcrumbs / blocks / enums / models.{names,attributes.base,attributes.<model>} / common / pages / helpers`. Приведение legacy-словарей у нас и так отложено в фазу 2 — значит, приводить надо к этой структуре.

### Новое, чего не было в разборе spa

4. **`<Entity>Crud`-DTO отдельно от списочного DTO** (§4) плюс билдеры дефолтов на фронте. Это законченный ответ на вопрос «как не дать create и edit разъехаться», причём типобезопасный: тип формы генерируется из бэкенда. Уместно ровно тогда, когда у нас появится первая пара create/edit.
5. **Конверт `grid` вместо отдельных пропов пагинации и фильтра** (§3) — на один проп меньше, и фронт всегда знает текущее состояние списка, не парся URL.
6. **Struct как единственный источник strong parameters**: `permit` выводится из набора полей DTO, а невалидный вход обрабатывается **глобальным** обработчиком с `redirect_back_or_to(inertia: { errors: … })`, без `valid?`-флоу в экшене. У нас laravel-data умеет и то и другое — вопрос в том, чтобы зафиксировать это конвенцией.
7. **Правила Mantine** (§7) — «только компоненты Mantine» и «в style props только токены». Двух строк в `AGENTS.md` нет, а от них зависит цельность редизайна.
8. **Правило про генераты** (§5): не правим руками, **и не откатываем вывод**. Техническая половина у нас запланирована (`types-check`), словесной нет.
9. **Правила из §8**, которые стоят почти ничего и ловят реальные классы багов: запрет обычных методов в контроллерах; `order` не в скоупе; предикаты на поля; schema и data в разных миграциях; единая точка получения локали; «разделяй получение и использование»; `reload` отдельной инструкцией; интеграционный тест на каждый экшен.
10. **Правила Sentry** — у нас Sentry подключён, а конвенций нет вообще. Правило про константный текст `capture_message` предотвращает засорение проекта иссью-однодневками.
11. **i18n как фабрика с мемоизацией клиентского инстанса** (§6) — у нас в плане уже фабрика, но можно взять сигнатуры и `buildInitialI18nStore` буквально; заодно это закрывает нынешнюю проблему двух инстансов i18next с разной конфигурацией.

### Что не берём

Transactional outbox (нет исходящих вызовов, потеря которых стоит денег), Sorbet-специфика, `ransack`/`pagy` (у нас spatie/query-builder и штатный пагинатор), event bus (у нас нет доменов, которые надо развязывать), attr_json / AASM-политика, слой `repositories` (наши модели небольшие, query-скоупы в них помещаются).

## 10. Два расхождения с нашим планом миграции — знать, но не обязательно менять

Монолит на двух развилках выбрал противоположное тому, что записано в [docs/frontend-migration.md](frontend-migration.md):

- **`mantine-datatable`** — у нас в плане «не добавлять, свой тонкий слой на Mantine `Table`», в монолите гем используется. Контекст разный: там таблицы с ransack-фильтрами, сортировками и сохранёнными наборами фильтров (в словаре есть целый блок `blocks.active_data_table_filters`), у нас максимум 6 колонок и сортировки нет вообще. Решение остаётся в силе; но если таблицы усложнятся, готовый прецедент есть.
- **`@mantine/form`** — у нас в плане «единственный источник истины состояния формы — Inertia `useForm`», в монолите `@mantine/form` в зависимостях. Наш аргумент (второе состояние + ручная синхронизация ошибок) не отменяется тем, что монолит выбрал иначе; просто стоит знать, что готовые Mantine-компоненты форм в монолите живут на его `getInputProps`, и при копировании кода оттуда это придётся переписывать.

Ни то, ни другое не повод править план — но раз монолит наш ближайший источник кода для копирования, расхождение лучше держать в голове заранее.
